# 风险局限性说明

> 反作弊的本质是"在服务端不信任客户端的约束下，尽可能识别异常行为"。
> 任何反作弊都有局限，本节明确列出 NeoRFAntiCheat 的已知短板与对策，
> 供部署者正确评估其能力边界。

## 1. ModList 查端的核心局限（必须知晓）

`/report` 强制查端通过 **Fabric 自定义 Payload** 请求目标客户端上报 ModList。
此机制存在**结构性盲区**：

| 场景 | 能否检出 | 原因 |
|------|:---:|------|
| Fabric Loader 正常注册的作弊模组 | ✅ | modId 出现在 ModList |
| **进程注入外挂**（DLL 注入等） | ❌ | 不经过 Fabric Loader，不在 ModList |
| **非 Fabric 作弊程序**（独立工具） | ❌ | 不是 Mod，无从上报 |
| **改包型外挂**（发包即作弊） | ❌ | 不改变 ModList，需靠原生检测 |

**结论**：ModList 查端只能"排除/命中" Fabric 生态内的作弊模组，
**无法**通过该手段检出注入型或非 Fabric 外挂。这部分必须依赖内置原生检测
（运动/战斗/交互/发包）兜底。

## 2. 反作弊的普遍局限

### 2.1 误判（False Positive）
- **卡顿误判**：服务端 MSPT 高、TPS 掉帧时，合法移动会被误判为瞬移/加速。
  - 对策：TPS 自适应（MSPT 高放宽阈值，TPS 过低跳过时序敏感检测）。
- **网络抖动**：高 ping 玩家的攻击距离、移动会被放大。
  - 对策：ping 补偿、多帧平滑。
- **残留风险**：即使有上述对策，仍可能误封。
  - 对策：`FALSE_POSITIVE` 标记不叠加次数，配合管理员复核机制兜底。

### 2.2 漏判（False Negative）
- 检测是启发式的，高手速/高技巧玩家可能接近阈值而不触发。
- 对策：阈值保守，宁漏勿误；依赖多次违规累计而非单次。

## 3. 客户端不可信原则

- 本项目检测**不信任客户端上报的任何数值**（速度、位置、战斗数据均以服务端为准）。
- 唯一例外是 ModList——但它只反映"Fabric Loader 注册了什么"，不代表客户端实际行为。

## 4. 对抗性绕过

作弊者可能：
- **移除黑名单 modId 的 mod 文件再进服** → 查端不再命中（但原生检测仍会兜底）。
- **伪装/篡改 ModList 响应** → 客户端需自行实现响应包，属客户端行为，服务端无法完全拦截。
  - 对策：把查端作为"辅助证据"，封禁始终以原生检测证据为主。

## 5. 性能与稳定性

- 移动类检测每 tick 全量玩家轮询，玩家多时有一定 CPU 开销。
  - 对策：`checkIntervalTicks` 可调（默认每 tick），Nuker/Item 等低频检测自带节流。
- Packet Flood 需要 netty 管道钩子，随 MC 内部结构变化，升级版本时需重新校订。

## 6. 结论与建议

1. 把 NeoRFAntiCheat 定位为**辅助反作弊**：原生检测兜底 + 查端辅助，不替代服务端主反作弊。
2. **误封复核是刚需**：务必配置管理员可用 `/NeoRF unban <uuid> falsepositive`，
   且误封不计次数，避免玩家被一次误判推入永久封禁。
3. 对**注入型外挂**高发的服，需配合更底层的服务端防护（如协议校验、插件白名单），
   本项目不覆盖该场景。
